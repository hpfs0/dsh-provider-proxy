# dsh-provider-proxy 版本与排期计划（缺陷修复轮）

- **基线**：v1.1.0（2026-11-05 发布）
- **编制日期**：2026-11-09
- **依据**：2026-11-09 全量缺陷排查（P0×1 / P1×3 / P2×7 / P3×16，共 27 项）+ 1 项包元数据小瑕疵
- **覆盖**：v1.1.1 → v1.3.0，以及其间的条件补丁
- **配套**：每版发布说明按 `RELEASE_NOTES_<版本号>.md` 编写，结构与 [RELEASE_NOTES_110.md](RELEASE_NOTES_110.md) 一致

版本号理由：

1. **1.1.1 只能是 patch**：修的是「写坏 / 测错」，不新增字段、不改变既有配置的含义，升级后行为只会变得更符合文档。
2. **1.2.0 必须是 minor**：`.*`、尾点、全角标点的归一化会改变既有规则的匹配结果；降级直连触发面收窄也是可感知的行为变化。两条都必须进发布说明的「行为变化」。
3. **1.3.0 是 minor**：备份加 `enableFallbackDirect` 需把 `BACKUP_VERSION` 从 2 提到 3；旧版本会按既有规则拒绝 v3 文件（设计如此），需在「升级与迁移」里写明降级前先导出 v2。

## 3. v1.2.0 — Routing Hardening（2026-11-27）

## 6. 发布检查单（每版照抄）

1. 从 `main` 切 `fix/1.1.1-*` / `feat/1.2.0-*` / `feat/1.3.0-*`；一个缺陷一个 commit（`fix(client): …` / `fix(host): …`）。
2. **先写失败用例再修**——这 27 条目前一条测试都没有，是整个缺陷清单的成因。
3. `npm run verify` 全绿（用例数预计 472 → 约 485 / 505 / 520）。
4. `npm pack --dry-run` 仍为 **9 个文件**；`package.json` 与 `README.md` 版本同步。
5. 写 `release_notes/RELEASE_NOTES_<版本号>.md`（1.2.0 必含「行为变化」，1.3.0 必含备份 v3 的迁移说明）。
6. `npm version patch|minor` → `git push --follow-tags`。
7. 双环境冒烟：编辑 → 导出 → 导入回环；改密码后立刻测试；改 `onlyHosts`；旁路开关；心跳开关。

## 7. 风险与回滚

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| P0-1 改的是所有设置写入的公共路径 | 可能引入新的写入回归 | 抽 `mergeDraft(stored, draft)` 纯函数，三处调用点共用；先补用例再改 |
| 1.2.0 改变既有规则的匹配结果 | 少数配置的走向会变 | 发布说明单列「行为变化」；诊断面板列出「含义已改变」的条目 |
| 1.2.0 收窄降级触发面 | 依赖 ECONNRESET 自愈的用户会觉得「不再自愈」 | README「故障容灾」写明新边界 |
| 备份 v3 被旧版拒绝 | 降级后无法导入新文件 | 「升级与迁移」明确：降级前先导出 v2 |
| 1.1.1 出现现场回归 | 数据面再次受损 | 48 小时内出 `1.1.2` 单点修复，**不整体 revert** P0 修复 |

## 8. 待确认事项

1. **备份 Schema v3 是否现在做**：加 `enableFallbackDirect` 会让 1.2.x 拒绝导入 1.3.0 的文件。建议做（否则「恢复＝整体替换」原则持续有缺口），放 1.3.0。
2. **P3-o 以谁为准**：建议按 README 渲染只读「目录中缺失」卡片（可关闭、可删除），而不是改文档迁就代码——否则用户没有任何入口处理那条仍在配置里、且可能带密码的路由。
